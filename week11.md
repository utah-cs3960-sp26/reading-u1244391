Emil’s first attempt at building JustHTML started as a from scratch parser where the agent slowly improved it by fixing bugs and passing more tests, eventually reaching full test coverage, but the structure and performance were not great and it ended up being slow and somewhat messy despite working correctly. In the second attempt he threw everything away and restarted, this time having the agent study and follow the design of html5ever from the beginning, which gave it a much better overall structure and direction. While things like fuzzing, benchmarks, profiling, and test coverage all helped improve correctness and performance later on, they were not the main reason the second attempt succeeded. The biggest difference was that the agent now had a strong reference design to guide it, instead of blindly discovering the architecture through trial and error. From html5ever the agent mainly gained ideas about how to structure the parser, how to organize the logic, and what kinds of data flows and abstractions to use, rather than just copying code directly. This meant the second version started with a much better foundation, making everything that came after easier and more effective. So while testing and performance tools were important, the most important change was giving the agent a clear architectural blueprint early on, which led to a cleaner, more coherent, and ultimately more successful implementation.

I think publishing software libraries built this way can be useful, but it also comes with some real risks, so it’s not always fully responsible without extra care. On one hand the library clearly works and passes a large test suite, which gives some confidence that it behaves correctly in many cases, but passing tests is not the same as deeply understanding the code or guaranteeing there are no hidden bugs or edge cases. The biggest concern is that the person publishing it may not fully understand how it works internally, which makes it harder to maintain, debug, or trust in critical situations. There are also questions around code quality, long term reliability, and whether subtle issues were introduced during the automated porting process that tests might not catch. If I were using JustJSHTML in a project I would be cautious about relying on it for anything important without additional review, more real world testing, and possibly reading through key parts of the code myself. I would also worry about long term maintenance, since if something breaks it might be difficult to fix without deep knowledge of the system. So while it is impressive and probably fine for experimentation or non critical use, I would hesitate to depend on it in production without stronger guarantees and more human validation.
